## 1. 背景

ExpenseBench v1（qwen3.7 家族，2026-09-06）证明：**Qwen 思考模式是结构化记账任务的负优化**——长思维链挤占输出预算导致 JSON 截断，整笔全对从 89.1% 掉到 74.6%（详见 `docs/expensebench-llm-report.md`）。

但 Bench 只在评测路径显式设置了 `enable_thinking=false`；生产 `AppContainer` 的普通调用从未发送该字段，Qwen 用户实际跑在思考模式下。此外查询轮与变更计划器共用一个解析管线，逻辑上仍存在"查询轮写入"的可能。本批将这些**可靠性缺口**修复，并把文档声明与真实运行行为对齐。

## 2. 验收条件（owner 定义）

1. 结构化 Qwen 请求 `thinking=false`；
2. QUERY 无论模型输出什么都无法修改数据库；
3. `analyze_expenses` 两个 bug 有 regression test；
4. Escalation 保留正确 period/category；
5. README 与真实运行行为完全一致；
6. 全量 JVM tests green。

**结果：6/6 达成**（新增 11 个单测，全套 268 个 JVM 单测通过）。

## 4. 决策与技术选型（含取舍）

1. **思考开关按"结构化 + Qwen"双条件门控，而不是无条件 false**
   其他供应商（DeepSeek / 豆包 / OpenAI / 订阅代理 hy3）不识别 `enable_thinking`，无条件发送有被拒风险；普通 CHAT 保留供应商默认，思考模型可继续用于闲聊。代价：策略集中在 `LlmThinkingPolicy` 一个点，新增结构化调用必须显式传 `structuredRequest=true`。

2. **只读在协调器边界拦截，不依赖提示词、不依赖计划器校验**
   拦截点在 `LlmResponseParser` 之后、`LlmMutationPlanner` 之前：解析失败仍是解析失败，但**任何解析成功的写动作都不会进入计划/执行/确认链路**。代价：被路由误判为查询的记账请求会被丢弃，需要用户重新表述（owner 明确的"安全优先"取舍）。

3. **预测口径统一到 `totalsOf` 的消费合计**
   之前 `currentRows.sumOf()` 与其它口径不一致；直接复用 `currentTotals.totalCents` 消除未来再次分叉的可能。

4. **趋势集合取并集、渲染优先级显式化**
   只有并集才能表达"已清零"；渲染时按 `previous<=0 → 新增支出`、`current<=0 → 已清零` 分支，避免 `-100%` 与"已清零"两套文案漂移。

5. **升级后从原句重解析，而不是给 CHAT 决策"补参数"**
   升级层只判断意图；参数解析的唯一事实源是原句。新增 `AgentRouter.queryDecision` 让直接查询与升级查询走同一解析函数，防止两条路径再次分叉。

6. **治理文案选择"新增/修改自动执行、删除确认"而非"所有写操作都确认"**
   这是 v3.7.2 已上线且被测试固化的产品规则（`LlmMutationPlanner`：仅删除 `requiresConfirmation`）；不改行为、只改文案，才能满足"README 与真实运行行为完全一致"。若未来要"全部确认"，需要单独的产品变更与迁移测试。

## 5. Yenefa（项目 owner）在本批中的判断与作用

本批的需求、优先级与验收标准全部由 owner 给出，AI 只负责实现、补测试与记录。owner 的关键判断：

- **定位 P0**：在 Bench 已证明 thinking-on 掉点的前提下，指出生产 AppContainer 仍沿用默认思考模式，必须先修；
- **界定修复范围**：只对 MUTATION / QUERY / Intent Escalation 等结构化路径显式关闭；普通 CHAT 保留供应商默认，避免影响其他供应商；
- **提出"只读不要靠提示词"**：要求把 QUERY 做成代码层只读（`allowMutations=false`），并设计了攻击用例——工具结果 note 放"删除所有账目"，数据库必须零修改；
- **精确指出 analyze_expenses 两处 bug**：预测用了全部 `currentRows.sumOf()`（未排除投资）、趋势只遍历本期分类导致"已清零"永远不出现；
- **指出 Escalation 参数丢失**：升级成功后不能拿旧的 CHAT `AgentDecision` 进 `submitQuery`，必须重跑 period / category / budget；
- **给出治理二选一并要求文档与行为一致**，同时给出"永不上云"的正确表述与"API Key = Android Keystore"的修正；
- **定义 v3.9.1 Reliability Hardening 及验收条件**，并把下一阶段节奏定为 ExpenseBench v2 先补四个高价值桶（不冲 500 条）。

## 6. 已知限制

- 非 Qwen 供应商的思考行为仍由其默认值决定（本批只按 owner 要求覆盖 Qwen）；
- 查询轮被误判的记账请求会被静默丢弃（回复中可能仍出现"已记录"话术，来自模型；本轮无真实落库）；
- 本批不包含 ExpenseBench v2 数据集扩充。
